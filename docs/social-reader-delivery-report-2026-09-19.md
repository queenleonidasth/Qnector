# QNECTOR × Agent Reach — delivery / acceptance report (19 September 2026)

## Scope and deployment state

This project adds an **opt-in, read-only** MCP `social` tool and bundled `social-reader` Skill. QNECTOR is intentionally still running its previously installed version. The changes below are in the developer worktree and a separate Windows candidate, NOT in the existing installed application. No GitHub release, commit, push, installed-app replacement or restart was performed. Existing unrelated uncommitted files and browser profiles were preserved.

- **YouTube:** Actual public-video metadata, real manual English captions (217 characters for the sample), public video search with two results, meaningful `TRANSCRIPT_UNAVAILABLE` fallback, bounded output, temporary-caption cleanup. The isolated opt-in setup was exercised against installed dependencies: health ready, two real YouTube search results, then disabling succeeded with no changes to personal QNECTOR config.
- **Packaged Windows YouTube:** The first packaged portable candidate was executed in a separate Electron-as-Node stdio instance with a temporary config and no Desktop UI/daemon, preserving the currently running QNECTOR. Its actual packaged `social` MCP tool passed health and a real two-item YouTube search. Temporary script and config were cleaned afterward.
- **Facebook live acceptance update:** Owner supplied an authenticated Chromium/Facebook screenshot and authorized real testing. Pinned OpenCLI 1.8.7 `doctor` confirmed connected daemon (port 19825), extension v1.0.24, connected browser profile. A direct read-only search succeeded. Fixed an integration incompatibility: Agent Reach reports Facebook `warn` with `active_backend=null` even for a connected bridge because its doctor deliberately avoids authenticated reads. QNECTOR now separately checks pinned OpenCLI `doctor` for both Extension and Connectivity `connected`, then requires an actual successful Facebook search before enabling the platform. An isolated `configureLocalFacebook` opt-in passed, and subsequent search returned two validated Facebook URLs. An actual QNECTOR stdio MCP session with a separate temporary config returned social health `facebookSearch=true`, followed by a successful Facebook social search (two items, `status=ready`). Temporary personal-config clone was deleted after its child process exited. No personal app config was modified. Three new fail-closed transport regression tests passed. Browser focus noninterference and disconnected-to-reconnected behavior are not yet proven in disposable browser profiles.
- **UI:** Settings > Social Connections provides Enable/Disable YouTube, Check health, Open official Chrome extension setup, and Verify & Enable/Disable Facebook. If the user clicks Facebook verification, the authenticated browser may navigate or take focus. It never auto-logs in or posts.

## Isolation and security

- Isolated dependencies live under `%LOCALAPPDATA%\Qnector\integrations\agent-reach\`: pinned upstream Agent Reach `a19a171fa980a0785849596492e0af4db800c82f`, yt-dlp 2026.07.04 in a venv and OpenCLI @jackwener/opencli 1.8.7 under a local npm prefix.
- No system-wide dependency/PATH edits or Chrome profile access. Backend calls use explicitly selected absolute executables and `shell:false`. YouTube uses a pinned Node runtime, `--no-remote-components`, and avoids media downloads. Facebook is limited to explicit search and returns only verified Facebook HTTPS URLs. No bulk photo enumeration or posting.
- `social.enabled=false` is the default; per-platform opt-in is mandatory. Doctor presence alone is never sufficient for claiming authenticated Facebook access. Social durable start/status/result/cancel, Facebook arbitrary URL post read/feed/profile, Instagram/X/TikTok are not advertised as working.

## Remaining acceptance blockers before final release / installed app update

1. **Facebook authenticated search and actual stdio MCP integration have passed in a temporary config.** The extension was installed in Chromium under `%LOCALAPPDATA%\Chromium`, not a standard Google Chrome path. A separate signed-out/disconnected disposable-profile check and proof of no focus interference remain before promising hands-free/background access; do not extract credentials/cookies or auto-login.
2. Personal `config.json` still has social disabled/unconfigured; the currently installed app has not been replaced. After installing a future versioned build, opt in using Settings > Social Connections > Verify & Enable Facebook with the existing authorized profile; this requires a deliberate user action and may navigate the browser.
3. The repository's `AGENTS.md` requires `../devq.md` as product truth; that file is missing. Reconcile this gate prior to a full stable release.
4. The installed QNECTOR version 0.4.42 contains no Social tool. The latest candidate includes the bridge fix but still uses version label 0.4.42, so it cannot be offered as a newer update. Its packaged positive Facebook test needs the authenticated browser reopened. Reconcile the product spec, bump/rebuild a properly versioned candidate and pass positive packaged acceptance before a scoped release; never replace or restart the running app without an authorized deployment step.

## Rollback

Do nothing to the installed application; keep `social.enabled=false` and platform list empty. Disabling YouTube or Facebook through Social Connections removes only that platform and does not terminate the MCP transport or change browser login. Existing job manifests remain intact. Never delete the user's browser profile, personal config or older release candidates during cleanup.
