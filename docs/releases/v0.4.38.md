# Qnector v0.4.38 — MCP latency and timeout mitigation

## Changes
- `process.run` starts a command once and returns its normal output for short operations; at 5 seconds it yields a tracked process ID and `running` state. Poll `process.output` and `process.task_get` to retrieve output and exit status without replaying side effects.
- The auto-escalated command has a separate, bounded execution timeout (maximum 10 minutes). Explicit `process.start` / `task_start` service processes are not killed merely because a request's wait budget elapsed.
- MCP process/workflow wait actions default to 3 seconds and are capped at 10 seconds per request, so long waits cannot occupy the upstream dispatcher for two minutes.
- SSE heartbeats remain guarded to `text/event-stream` frames and never corrupt JSON. Tool-progress notifications are emitted every 10 seconds *only when* an MCP client supplies a progress token; diagnostics record presence and failures without logging token contents.
- Metadata-only timeline logs capture request/tool/response phases. A diagnostic timeout probe is opt-in and is not published in the normal tool list.
- Opt-in durable runtime foundation and packaged daemon/recovery gates included from the current feature branch.

## Verification / limitations
- Local full suite: 302/302 passed before final release version bump; additional targeted checks and the final packaging gate must pass before publication.
- Typecheck, lint, build and local MCP smoke succeeded before version bump; rerun release checks after version changes.
- ChatGPT Web/tunnel eight-case end-to-end timeout probe and installed-build reconnect soak tests have **not** been completed; this release must not be presented as a proven cure for all browser-side connection interruptions.
- The auto-escalated `process.run` tracking is process-manager memory scoped; for work that must survive Qnector restarts, use the explicit durable task API when verified and available.
